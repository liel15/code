## 문맥

이 변경은 하나의 메모를 마라탕 조리 장면으로 바꾸고, 그 결과를 히스토리 목록에 보존하는 데스크톱 웹 경험을 추가합니다. 핵심 과제는 백엔드 연동이 아니라, 여러 UI 상태와 드래그 상호작용, 맵기 상승, 저장된 히스토리/상세 복원을 하나의 일관된 클라이언트 흐름으로 묶는 일입니다.

진입 시에는 최대한 단순해야 하고, 조리 화면으로 들어가면 더 표현적인 장면으로 확장되어야 합니다. 또한 이전 메모를 다시 열어도 저장된 마라탕 상태가 유지되어야 합니다.

## 목표 / 비목표

**목표:**
- 시작, 조리, 먹기, 기절, 완료, 상세를 명시적인 UI 상태로 모델링합니다.
- 메모 히스토리를 로컬에 보존하고, 이전에 만든 마라탕 장면을 다시 열 수 있게 합니다.
- 재료 드래그와 마우스 중심의 먹기 동작을 데스크톱 우선으로 지원합니다.
- 맵기, 영수증, 완료 피드백을 항상 읽기 쉽게 유지합니다.

**비목표:**
- 백엔드, API, 인증 작업은 하지 않습니다.
- 다중 사용자 협업은 포함하지 않습니다.
- 기본 반응형 대응을 넘는 모바일 우선 최적화는 하지 않습니다.
- 영수증은 시각/놀이 요소일 뿐, 복잡한 상거래나 결제 로직은 포함하지 않습니다.

## 결정 사항

### 1. 화면 흐름은 상태 머신으로 관리한다
UI는 조건문이 흩어진 방식이 아니라 작은 유한 상태 집합으로 구동해야 합니다. 그래야 전환이 예측 가능하고 저장된 메모 복원도 쉬워집니다.

대안:
- 라우트 전용 흐름: 딥링크에는 유리하지만, 일시적인 놀이 상태를 다루기 어렵습니다.
- 단순 컴포넌트 토글: 초반에는 쉽지만, 기절/완료/히스토리 복원이 추가되면 추론이 어려워집니다.

### 2. 메모 히스토리는 클라이언트에 저장한다
메모 히스토리와 저장된 마라탕 데이터는 클라이언트 저장소를 사용합니다. 이 앱은 단일 사용자 놀이 경험이므로 로컬 저장만으로 충분하고, 백엔드 의존성을 늘리지 않습니다.

대안:
- 서버 저장: 동기화에는 좋지만 초기 범위에는 불필요하고 제품 복잡도만 높입니다.
- 메모리 전용: 새로고침 시 히스토리가 사라져 너무 취약합니다.

### 3. 영수증은 파생 뷰로 처리한다
영수증은 별도 원본으로 저장하지 않고, 현재 재료 목록과 맵기, 메모 제목으로부터 계산합니다. 이렇게 하면 중복이 줄고 시각 요약이 게임 상태와 어긋나지 않습니다.

대안:
- 영수증 항목을 따로 저장: 중복되고 동기화가 어긋날 가능성이 큽니다.

### 4. 드래그는 포인터 우선, 클릭은 보조로 둔다
주요 상호작용은 마우스 입력에 맞춘 포인터 이벤트와 드래그 감각을 사용합니다. 드래그가 불편한 경우에는 클릭 동작을 보조로 제공해 접근성과 안정성을 확보합니다.

대안:
- HTML5 드래그앤드롭만 사용: 가능하지만 richer feedback을 만들기에는 어색한 경우가 많습니다.
- 클릭 전용: 더 견고할 수 있지만, 놀이감과 컨셉 적합성이 떨어집니다.

### 5. 맵기 상승은 시간 기반 놀이 규칙으로 만든다
먹기 동작은 충분히 빠르게 맵기를 올려 긴장을 만들고, 100에서 10초 기절을 발생시킵니다. 이렇게 해야 반복 먹기가 수동 애니메이션이 아니라 선택이 됩니다.

대안:
- 높은 맵기에서 완만한 상한: 안전하지만 긴장감이 약합니다.
- 기절 패널티 없음: 먹는 화면의 핵심 위험/보상 구조가 사라집니다.

### 6. 상세 화면은 저장된 장면을 복원한다
히스토리 항목은 일반 메모 페이지가 아니라 저장된 마라탕 장면을 재구성하는 상세 화면을 열어야 합니다. 이 앱의 정체성은 메모를 보존된 음식 장면으로 보는 데 있습니다.

대안:
- 일반 메모 상세: 더 단순하지만 핵심 은유가 사라집니다.

## 위험 / 트레이드오프

- [조리, 먹기, 기절, 복원까지 상태 복잡도가 커짐] → 전환은 하나의 공유 흐름 모델로 관리하고 각 상태의 종료 조건을 명확히 둡니다.
- [드래그 상호작용이 브라우저마다 다르게 느껴질 수 있음] → 포인터 이벤트를 사용하고 클릭 보조를 제공하며, 마우스 기반 데스크톱 브라우저에서 우선 검증합니다.
- [로컬 저장 데이터가 오래되거나 손상될 수 있음] → 저장 데이터 형식을 버전 관리하고, 파싱 실패 시 안전한 기본 상태로 되돌립니다.
- [컨셉이 시각적으로 과해질 수 있음] → 시작 화면은 비워두고, 동시 제어 수를 제한하며, 영수증은 편집 불가 파생 정보로 유지합니다.

## 마이그레이션 계획

1. 기존 진입 흐름 뒤에 새로운 상태 모델과 저장 데이터 형식을 도입합니다.
2. 같은 로컬 저장소를 사용해 히스토리 사이드바와 상세 복원을 추가합니다.
3. 조리 상호작용, 영수증 파생, 맵기 진행을 추가합니다.
4. 먹기/기절/완료 루프를 추가하고 시간 규칙을 검증합니다.
5. 새로고침 후와 히스토리 재진입 후 복원 상태를 검증합니다.

## 결정된 사항

- 첫 버전의 조리 시작 상태는 국물만 있는 빈 냄비로 시작하고, 이후 재료는 사용자가 선택해서 추가합니다.
- 히스토리에는 조리 전체 타임라인을 저장합니다.
- 탭이 백그라운드로 가더라도 10초 기절 타이머는 그대로 진행합니다.
- 상세 화면에서는 왼쪽 히스토리 패널을 접어서 마라탕 장면이 더 넓게 보이도록 합니다.
